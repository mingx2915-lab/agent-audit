# 知盾 AgentAudit 产品体验与比赛表达收口审计

> 状态：Accepted / F-060 本地实现已完成  
> 日期：2026-09-01  
> 当前边界：本文档的本地可实现项已由 F-060 收口；未修改 Security Contract、Trace、Finding 或 Replay 判定，真实企业与陌生用户证据仍保持未验证。  
> 用户反馈来源：实际启动和操作软件时出现错误原因不清、下一步不明确；界面存在小字、排版和视觉完成度不足；主要表达偏技术，比赛评委难以快速理解。

## 1. 结论

知盾 AgentAudit 当前已经具备较强的工程实现、真实运行链路和验收证据，但产品层仍存在三个相互关联的问题：

1. **看不清**：小字、低对比度、卡片和间距规则不统一，页面功能完整但视觉完成度一般；
2. **不会用**：首次启动时缺少真正可执行的单任务路径，错误只说明“失败”，没有稳定说明原因、影响和恢复动作；
3. **看不懂**：页面仍大量使用 Provider、Contract、Plan、Actor、Source、Sink、Trace、Finding、Replay、Ground Truth 等工程概念，评委需要先理解系统实现，才能理解项目价值。

这三条不能分别用“调大字号”“多写教程”“翻译几个术语”解决。它们的共同根因是：

> 当前软件主要按工程模块和数据结构组织信息，而首次用户和比赛评委需要按任务、风险和结论组织信息。

后续收口目标应是：

> **首次用户会用，比赛评委看懂，专业人员仍能核对完整证据。**

## 2. 事实、判断与尚未验证内容

### 2.1 已确认事实

- F-035 的软件实现和自动化链路已经完成，但“从空白启动到首个 Guided Audit 控制在五分钟内”和“由未阅读源码的人独立完成任务”仍未验收；
- F-045 已建立 Typography 和宽屏 tokens，但实施范围明确只覆盖设计系统基础和两个重点工作区，并非全站迁移；
- 当前 `apps/web/src` 仍包含大量组件内硬编码字号。静态扫描得到 557 处像素字号声明，其中 464 处为 12px 或更小。该数字包含可能被后续样式覆盖的历史声明，不能等同于 464 个当前可见缺陷，但足以证明样式规则仍然分散；
- F-059 已解决攻击链内部符号、节点展开拉高整行、Finding 编号漂浮和完整 Trace 过小等局部问题，但没有完成全软件的用户表达和视觉收口；
- 当前首次向导中的“使用合成演示”写有“立即查看固定演示资料、真实 Trace、Finding 和 Replay”，实际运行仍要求先连接 Provider，用户预期与前置条件不一致；
- 首页选择向导下方仍常驻渲染完整 Provider Setup、资料导入和核心验收模块，用户选择一条路径后，页面没有真正收敛为单步任务；
- Provider Setup 将加载、发现、地址检查、Readiness 和保存等多个阶段的错误聚合为一条显示字符串，缺少统一的错误类型、阻塞级别和恢复动作契约；
- 应用加载时并行读取多个业务模块。系统故障时，不同模块可能分别呈现错误，首次用户无法判断哪个才是当前必须处理的问题。

### 2.2 产品判断

- 当前产品更接近“功能成熟的内部工程工作台”，尚未达到比赛现场所需的成品化表达；
- 用户遇到错误后长时间不知道原因和下一步，不属于用户学习能力问题，而属于首次使用与错误恢复设计未完成；
- 评委如果需要理解 DTO、ID、协议或英文缩写才能理解创新点，软件展示就没有替答辩者完成信息翻译；
- 继续逐张截图修 CSS 可以改善局部，但会重复产生新问题，不能建立稳定的产品品质。

### 2.3 尚未验证

- 尚无未阅读源码的陌生用户，从空白安装状态独立完成五分钟首次验收的正式记录；
- 尚未对 Ollama 未启动、无模型、企业地址错误、401、超时、Provider 502、文件无权限和解析失败等真实错误路径做完整人工可恢复性验收；
- 尚未证明评委在不听开发者解释的情况下，可以仅通过界面复述产品价值、风险过程和 Replay 结果；
- 当前审计没有把真实企业 Gateway 或真实企业数据写成已验证能力。

## 3. 三类目标用户与三层信息

同一份运行事实需要面向三类用户提供不同阅读层，不能让所有人直接阅读同一份工程数据。

| 用户 | 首要问题 | 默认应看到 | 不应成为前置知识 |
|---|---|---|---|
| 比赛评委 | 这个项目解决什么问题，有什么创新，结果可信吗 | 业务风险、攻击过程、权限判断、修复前后结果 | DTO、JSON、内部 ID、协议字段 |
| 首次使用者 | 我现在要做什么，为什么失败，怎么继续 | 当前步骤、唯一主操作、缺少条件、恢复动作 | Workspace、Retriever、Profile、operation ID |
| 专业人员 | 结论由什么证据支持，能否追溯 | Rule、Trace sequence、Provider、Runtime、原始事件 | 无；但这些内容默认进入技术详情 |

产品必须使用三层信息结构：

### 第一层：业务结论

回答评委和普通用户最关心的三个问题：

1. AI 做了什么不该做的事；
2. 风险发生在哪一步；
3. 调整规则后，同一个问题是否被阻止。

### 第二层：可核对证据

展示身份、内容来源、读取资料、权限判断、工具动作、数据去向和前后差异，但使用中文业务语言。

### 第三层：技术详情

保留 Provider、Security Contract、Rule ID、Plan ID、Trace ID、时间戳、原始 JSON、Runtime 和 operation ID。该层必须可访问，但不占据默认比赛阅读层。

三层只改变展示投影，不得修改或补造底层事实。

## 4. 面向比赛的统一产品表达

### 4.1 一句话说明

建议默认使用：

> 知盾会在企业知识助手上线前，模拟内部越权和外部恶意内容，检查 AI 是否读取了不该读取的资料、调用了不该调用的工具，或把敏感信息发送到外部；发现风险后，再用同一个攻击进行复测。

技术版说明可以保留在展开区：

> 系统以 Security Contract 描述业务权限，通过 Retrieval、Authorization、Tool Call 与 Sink 全过程 Trace 生成 Finding，并执行同 Plan Replay。

### 4.2 评委应记住的三个价值点

1. **测的是业务权限，不只是 Prompt 是否“有害”**；
2. **同时测试内部合法用户滥用和外部不可信内容诱导**；
3. **不仅发现问题，还保留全过程证据，并用同一攻击验证修复效果**。

### 4.3 五分钟比赛叙事

| 时间 | 界面要回答的问题 | 评委应获得的结论 |
|---|---|---|
| 0:00–0:30 | 软件是做什么的 | 上线前检查企业 AI 的业务权限风险 |
| 0:30–1:00 | 今天测试什么 | 财务人员受到外部文档诱导，可能外发机密资料 |
| 1:00–2:00 | 系统如何检查 | 从内容进入、读取资料、权限判断、工具调用到数据去向完整记录 |
| 2:00–3:00 | 发现了什么 | 权限虽然拒绝，但外部发送动作仍发生，构成 Critical Finding |
| 3:00–4:00 | 如何证明不是猜测 | Finding 对应明确 Rule 和 Trace 证据序列 |
| 4:00–5:00 | 修复是否有效 | 使用同一 Plan Replay，比较修复前后实际行为 |

默认演示过程中不要求评委阅读完整 JSON、模型请求体或内部英文 ID。

## 5. 技术语言到比赛语言的投影规则

技术术语不删除，但在默认层使用业务表达，在技术详情中保留原词。

| 技术概念 | 默认业务表达 | 技术详情保留 |
|---|---|---|
| Provider | AI 运行环境 / 已连接的模型服务 | Provider kind、protocol、base URL、model |
| Security Contract | 企业权限规则 | Contract ID、version、完整规则 |
| Actor | 操作人 / 当前身份 | Actor ID、role |
| Source | 内容从哪里进入 | source type、trust level |
| Resource / Retrieval | AI 读取了哪些资料 | document ID、labels、score、model context |
| Authorization | 权限是否允许 | decision、Rule ID、reason |
| Tool Call | AI 执行了什么业务动作 | tool name、arguments、result |
| Sink | 数据最终去了哪里 | sink type、destination、external |
| Finding | 发现的风险 | Finding ID、severity、evidence sequence |
| Trace | 完整过程证据 | event type、event ID、timestamp、raw details |
| Replay | 使用同一攻击重新检查 | Replay ID、before/after Trace |
| Ground Truth | 固定标准测试题 | Case ID、Expected、Actual、metrics |
| Differential | 不同身份对比 | task ID、profile、actor matrix |
| Acceptance Run | 完整验收 | Run ID、Gate、artifact、checksum |

### 5.1 页面表达顺序

每个核心区块统一按以下顺序组织：

```text
结论标题
→ 一句业务解释
→ 当前状态或唯一主操作
→ 关键证据
→ 技术详情
```

禁止继续使用以下顺序：

```text
英文 kicker
→ 内部 ID
→ DTO 字段
→ 大段边界声明
→ 最后才出现结论
```

### 5.2 文案约束

- 页面和区块标题优先使用动作或业务结果，不使用模块类名；
- 主标题优先控制在 12 个中文字符以内，说明优先控制在 28 个中文字符以内；
- 主界面只保留必要 English technical terms，不进行中英文重复朗读；
- Rule、Profile、Expected、Actual、matched、runtime 等字段不直接平铺到默认阅读层；
- “真实”“明确”“当前”“只会”“这里将”等无信息增量词只在事实边界需要时使用；
- 不用增加更多解释段落解决不会用的问题，优先改变流程、状态和按钮；
- Finding、Replay、Trace 等保留原术语时，首次出现必须同时给出中文含义。

## 6. 首次使用路径

### 6.1 首屏只能提供一个决策

推荐首屏提供两个互斥入口：

#### 路径 A：快速了解产品

```text
查看明确标注的内置示例
→ 看懂一次风险过程
→ 查看 Finding
→ 查看 Replay 前后对比
```

该路径不得声称刚刚调用了真实企业 Provider。若展示保存的示例证据，必须明确标注“内置示例 / 非本次新执行”。

#### 路径 B：开始一次真实验收

```text
连接 AI
→ 添加业务资料
→ 确认权限规则
→ 选择检查目标
→ 运行
→ 查看结论与 Replay
```

进入路径后，一次只显示当前步骤和必要上下文。完整 Provider Setup、Document Import、Contract Editor 和高级证据不能全部继续纵向常驻。

### 6.2 状态必须区分“未配置”和“出错”

| 状态 | 含义 | 默认视觉 | 用户动作 |
|---|---|---|---|
| 待完成 | 用户还没有提供必要信息 | 中性提示 | 去完成 |
| 检查中 | 系统正在验证 | 进度状态 | 等待或取消 |
| 已就绪 | 当前步骤可继续 | 成功状态 | 下一步 |
| 需要处理 | 已执行检查且存在可恢复问题 | 警告/错误 | 按建议修复并重试 |
| 执行失败 | 已开始任务但没有得到有效结果 | 错误状态 | 查看原因、重试或导出诊断 |

没有配置 Ollama、没有选择模型或尚未导入资料属于“待完成”，不能在用户刚打开软件时表现为系统已经失败。

### 6.3 错误信息契约

所有用户可见错误至少包含：

1. **发生了什么**：使用业务动作描述失败阶段；
2. **可能原因或已确认原因**：只写系统能证明的事实，不猜测；
3. **影响**：说明当前不能继续哪一步，其他数据是否安全；
4. **处理动作**：提供明确按钮，而不是只写“请重试”；
5. **技术详情**：状态码、operation ID、原始诊断和时间放入折叠区。

示例：

```text
无法连接本机 Ollama

本机地址 127.0.0.1:11434 没有响应，因此暂时不能检查模型能力。
已保存的资料和验收记录没有受到影响。

[重新检测] [查看本机模型说明]

技术详情 ▾
```

### 6.4 多个问题的呈现顺序

系统同时存在多个问题时，不在页面不同位置同时堆叠红色错误。应按依赖顺序突出一个当前阻塞项：

```text
本机后台
→ AI 连接
→ 业务资料
→ 权限规则
→ 检查计划
→ Scan / Replay
```

非阻塞问题进入“还需处理的事项”，完成当前步骤后再提升为主任务。

## 7. 视觉与排版收口规则

### 7.1 字号

沿用已建立的语义 Typography，不以全局 `zoom` 代替组件迁移。

| 语义 | 建议规格 | 使用范围 |
|---|---:|---|
| Display | 40 / 48 / 56px | 每个主工作区最多一个核心主张 |
| Page title | 30 / 34 / 38px | 页面标题 |
| Section title | 23 / 26 / 29px | 一级功能区 |
| Card title | 18 / 19 / 21px | 结果卡、详情面板 |
| Body | 15 / 16 / 17px | 结论、说明、操作帮助 |
| Body small | 13 / 14 / 15px | 次级说明、时间、补充信息 |
| Label | 12 / 12 / 13px | 字段名、状态辅助标签 |
| Code / ID | 13 / 13 / 14px | Rule、Plan、Trace、operation ID |

约束：

- 用户必须阅读的说明不低于 14px；
- 8–10px 只允许用于非必要装饰序号，不能承载结论、错误原因或下一步；
- Monospace 只用于 ID、Rule、序列、时间和代码，不用于普通中文标签；
- 浅灰色不能承载关键状态、错误原因和操作说明；
- 标准/大字切换保留，但“大字”不能成为弥补基础字号过小的唯一手段。

### 7.2 页面节奏

- 一个视口或一个任务区最多一个实心主按钮；
- 卡片只用于独立任务、Finding 和 Replay 对比，不给每个字段、空态和说明都套卡片；
- 统一页面标题起点、内容宽度、卡片 padding、区块间距和按钮高度；
- 长列表使用“列表 + 选中详情”，长证据使用摘要 + 展开，不继续纵向全量平铺；
- 高级功能使用二级导航或折叠区，不与核心比赛路径同权重；
- 不能通过固定高度截断 Rule、错误、风险结论或证据。

### 7.3 颜色与图片

- Action Blue 只表示当前主操作；
- Risk Coral 表示真实风险或执行失败；
- Evidence Teal 表示通过、可信证据或 Replay 后状态；
- Warning Amber 表示等待确认、部分可用或可恢复问题；
- 未配置使用中性色，不使用红色；
- 继续保留启动、运行中、Critical Finding、Replay 前后四类具有状态意义的原创视觉；
- 不再用新增大图掩盖信息架构问题；图片不能替代真实状态和数据。

## 8. 核心页面目标

| 页面 | 当前主要问题 | 收口后的默认目标 |
|---|---|---|
| 首次启动 | 向导与完整模块同时出现，第一步不明确 | 两条互斥路径、一个当前任务、一个主按钮 |
| 连接 AI | 未配置与失败混淆，错误缺少恢复动作 | 说明需要什么、检查什么、如何修复；技术探针折叠 |
| 添加资料 | 普通用户仍需理解 Workspace 和元数据 | 先说明选择什么资料、如何使用、完成后去哪 |
| 核心验收 | 真正主操作出现较晚 | 首屏明确“今天验证什么”和“开始检查” |
| 攻击链 | F-059 已改善，但技术证据仍需分层 | 默认讲清谁、内容、资料、权限、动作、去向 |
| Finding | 指标与 ID 容易抢过业务结论 | 先说发生了什么和为什么危险，再给 Rule 与序列 |
| Replay | 边界声明和技术字段密集 | 先比较修复前后业务行为，再展示配置与 Trace |
| 验收证据 | 多个工具纵向合集，评委难判断重点 | 本次结论、历史证据、质量实验三层入口 |
| 高级设置 | DTO 字段和实验工具过多 | 面向专业人员保留，但退出比赛默认路径 |

## 9. 推荐实施顺序

三类问题应作为一个产品体验收口计划处理，但按真实用户旅程分成可验收增量，而不是一次性重写全站。

### 增量 A：首次启动与错误恢复

结果目标：用户首次打开软件后，只看到当前任务；没有配置时不出现误导性红色错误；所有阻塞问题都有直接恢复动作。

重点范围：

- 首屏双路径；
- 当前步骤隔离；
- Provider、资料与 Scan 的统一问题状态；
- Ollama、企业地址和文件错误恢复；
- 结构化错误展示和技术详情。

### 增量 B：比赛业务表达与核心叙事

结果目标：评委不理解内部术语，也能看懂项目解决的问题、风险发生过程和 Replay 价值。

重点范围：

- 产品一句话主张；
- 核心验收、攻击链、Finding、Replay 的三级信息层；
- 技术术语到业务表达的确定性投影；
- 五分钟演示阅读顺序；
- 验收证据页的信息分层。

### 增量 C：全站设计系统迁移与视觉精修

结果目标：消除组件间字号、间距、颜色和操作层级不一致，使软件从工程工作台提升为统一产品。

重点范围：

- 清理实际生效的 8–11px 可读文字；
- 统一 Typography、spacing、surface、status 和 button tokens；
- 收敛重复 scoped 样式和 `!important`；
- 统一卡片、表格、空态、错误、折叠证据和响应式布局；
- 对关键状态建立视觉回归。

### 增量 D：真实用户与比赛场景验收

结果目标：不由开发者解释，真实用户和模拟评委仍能完成任务、理解结论并从错误中恢复。

重点范围：

- 空白安装；
- 标准和大字两种显示；
- 1440、1920 和 390 三档视口；
- 未配置、检查中、已就绪、Finding、Replay、错误六类状态；
- 至少一名未阅读源码的用户；
- 一次五分钟比赛演示复核。

本地实施已按仓库规则建立并完成 F-060，实际状态与证据见 `docs/features/F-060-first-use-competition-experience-closure.md`；本文档仍作为产品审计与后续视觉检查基线，不替代真实陌生用户验收。

## 10. 验收标准

### 10.1 首次用户

- 打开软件 10 秒内能说出软件用途和当前唯一下一步；
- 未配置 Provider、模型或资料时不出现误导性的系统失败；
- 每个阻塞错误均包含发生阶段、可确认原因、影响、恢复按钮和技术详情；
- Provider 已具备的前提下，从空白状态到首个 Guided Audit 不超过五分钟；
- 用户无需阅读源码、README 或由开发者口头指导；
- 关闭并重开后能从真实保存状态继续，不自动重跑模型或外部动作。

### 10.2 比赛评委

- 30 秒内能复述项目解决的是企业 AI 业务权限验收问题；
- 不展开技术详情也能理解内部滥用、外部诱导、权限判断、工具动作和数据去向；
- 能从界面回答“发生了什么、证据在哪里、修复后是否有效”；
- 五分钟演示中不要求阅读 JSON、内部 ID 或英文 DTO 字段；
- 所有结论仍可展开到真实 Rule、Trace 和 Runtime 证据。

### 10.3 视觉质量

- 关键正文、错误原因和操作说明达到可读字号与对比度；
- 同级标题、卡片、按钮、状态和间距使用统一规则；
- 一个任务区只有一个主操作；
- 展开证据不拉伸无关卡片、不制造大面积空白、不产生页面级横向溢出；
- 1440×900、1920×1080、390×844 和 Desktop 默认窗口均完成真实视觉复核；
- 标准/大字模式不依靠隐藏内容或截断证据维持布局。

### 10.4 工程与事实边界

- 不修改 Security Contract、Trace、Finding、Replay 和权限判定语义；
- 不把保存的示例证据冒充本次新执行结果；
- 不自动扫描局域网、下载模型、启动外部攻击或发送真实邮件；
- 首次使用流程仍复用真实 API 与状态，不在前端复制判定；
- 原始技术证据继续可访问；
- Web typecheck/build、相关 Python/Rust 检查、关键 Playwright E2E 和 Desktop runtime 复核通过后才能宣告完成。

## 11. 失败场景验证矩阵

| 场景 | 默认层应说明 | 必须提供的动作 | 技术详情 |
|---|---|---|---|
| Ollama 未启动 | 本机模型服务没有响应 | 重新检测、查看启动说明 | loopback 地址、operation ID |
| Ollama 无模型 | 服务可用但没有可选择模型 | 打开模型管理说明、重新查找 | 返回模型数量 |
| 企业地址错误 | 当前地址无法连接 | 修改地址、重新检查 | origin、状态码；不显示 Secret |
| 认证失败 | 凭据未通过目标服务验证 | 重新输入凭据 | 401/403、operation ID |
| 请求超时 | 目标在规定时间内未完成响应 | 重试或修改连接 | timeout stage、duration |
| Provider 运行失败 | 本次 Scan 没有得到有效模型结果 | 重试、返回连接检查 | status、diagnostic |
| 文件无权限 | 所选文件无法读取，Workspace 未写入 | 重新选择、查看失败项 | 文件相对显示名、错误类型 |
| 文件不支持或损坏 | 部分项目不能解析 | 移除失败项、继续 Preview | format、parser diagnostic |
| Contract 无有效 Plan | 当前规则不足以生成检查 | 查看权限规则缺口 | missing role/rule |
| Scan / Replay 失败 | 本次执行未形成有效结论 | 重新执行、导出诊断 | scan ID、attempt ID、operation ID |

## 12. 不采用的做法

- 不通过增加更多说明段落代替任务流设计；
- 不通过全局放大或浏览器 zoom 代替语义字号迁移；
- 不机械地把所有技术词翻成不准确的中文；
- 不删除原始证据来让页面显得简洁；
- 不把所有功能改成同样大小的卡片；
- 不继续增加与真实状态无关的科技图片、光效和动画；
- 不用大量 `!important`、固定高度或局部覆盖掩盖布局根因；
- 不把 Test-only Provider、合成数据或保存示例写成真实企业验收；
- 不在本轮扩展 IAM、SSO、任意外部扫描或企业 Connector。

## 13. 关键风险与待决定事项

1. **快速了解产品如何实现**：推荐优先展示明确标注的保存示例；若要提供无需外部模型的新执行演示，需要另行决定是否引入正式、明确标注的确定性合成 Provider，不能偷偷使用 Test-only Transport；
2. **真实模型的不稳定性**：比赛现场使用 Ollama 或企业 Provider 时必须保留连接预检和可诊断失败，不能用自动 fallback 隐藏；
3. **简化与证据完整性的冲突**：默认层可以精简，但 Rule、Trace、Runtime 和原始事件必须继续可核对；
4. **全局 CSS 迁移风险**：应按关键旅程逐屏迁移并建立视觉回归，不进行无法审阅的一次性机械替换；
5. **陌生用户证据仍缺失**：开发团队自测和自动化不能替代最终的首次用户任务验收。

## 14. 完成定义

本轮产品体验收口只有同时满足以下条件才可宣告完成：

- 首次用户知道做什么，并能从常见错误中恢复；
- 比赛评委不依赖工程术语也能看懂核心价值和结果；
- 默认界面具备统一、清晰、可读的视觉层级；
- 专业人员仍能追溯完整技术证据；
- 演示、合成、真实运行和外部未验证边界标记准确；
- 自动化回归、真实 Desktop 复核、五分钟演示和陌生用户任务均有实际证据。

在此之前，项目可以描述为“核心功能与工程证据完整度较高”，但不能把首次使用体验、比赛表达和全站视觉完成度写成已经收口。
