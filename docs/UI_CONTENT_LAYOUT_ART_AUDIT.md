# 知盾 AgentAudit 全软件文字、排版与美工审计（Draft）

> 状态：Draft，边看真实桌面软件边记录。本文档只做审计与下一阶段建议，不代表已实施功能，不修改业务逻辑。

## 1. 审计目标

- 评委在 20 秒内能否看懂软件做什么、当前要点哪里、结果要看什么；
- 首次用户在不读源码和项目文档的前提下，能否完成连接 AI、添加资料、理解 Contract 与开始验收；
- 文字是否精简、人话、有层级，是否存在 AI 式并列、重复解释和中英混排过多；
- 排版是否突出主线“设置 → 扫描 → Finding → Replay”，美工是否帮助理解而不是占位；
- 桌面 1440×900 与窄屏下的字号、对比度、留白、拖长与操作可达性。

## 2. 审计方法与边界

- 以 2026-08-30 当前 Git HEAD 的 Tauri 桌面开发版真实窗口为准；
- 按主导航逐屏检查：核心验收、高级设置、完整审计、证据与评测；
- 区分“真实界面事实”、“评审判断”和“建议”；
- 本轮不更改 UI、不调用真实模型、不生成 Finding，避免审计时改变用户数据。

## 3. 全局初步结论

### P0：首页同时承担太多主线

**真实观察**

- 1440×900 首屏同时显示四顶导航、首次向导、两种连接方式、候选 Readiness 开头，下方还继续堆叠资料和核心验收；
- “从连接 AI 到第一次安全验收”和“连接 AI”在同一首屏分别开启一条视觉主线；
- 右侧小状态卡“尚未连接 AI”与下方整个连接区重复表达同一事实。

**评审判断**

- 用户需要在多个大卡中自行判断当前主操作，容易形成“软件功能很多，但第一步不明确”的印象；
- 评委首屏注意力被平均分配，无法立即聚焦“开始核心验收”。

**建议**

- 将首页收敛为一个“当前任务”卡：演示模式直接引导开始验收，自有助手模式显示 1–2–3 步进度；
- 首页不常驻展开完整 Provider Setup，改为紧凑状态+单一下一步；完整编辑放在“高级设置”或向导弹层/展开区；
- 同一屏只保留一个主按钮，其他入口降为次级文本操作。

### P1：字号和灰度对比偏弱

**真实观察**

- 顶部导航副标、卡片说明、英文 kicker 和技术标识在 1440×900 窗口中明显偏小；
- 多处浅灰文字与浅灰/浅蓝背景对比不足，例如首次向导说明、连接卡次级文字。

**评审判断**

- 这种“精致小字+低对比”在截图中整齐，但现场投屏和非高分屏上会降低可读性；
- 中文、英文、编号、状态同时出现时，视觉噪声大于信息增量。

**建议**

- 正文最小可见字号统一提高一档，次要文字优先加深而不是加粗；
- 英文 kicker 只保留品牌和必要技术证据，不对每个中文状态做英文复述；
- 以现场 125%–150% 显示缩放和投屏视距作为验收基线。

## 4. 逐屏审计

### 4.1 核心验收·首屏

- 优点：顶部品牌区、四工作区导航和主体卡片边界明确；浅色工作台比连续深色界面更容易长时阅读；
- 问题：四导航卡高度与首次向导卡高度叠加，在看到真正 Scan 按钮前需长距离滚动；
- 问题：“FIRST RUN · 5 MINUTES”、“从连接 AI 到第一次安全验收”、“先告诉软件……”、“不上传文件……”同时竞争，可减为一个标题、一个边界标签和两个选项；
- 问题：“选择连接方式并完成兼容性检查”、“尚未连接 AI”、“自动只查本机……”与下方操作本身重复；
- 建议：将首屏纵向长度压缩约 30%–40%，首次向导和当前 Provider 状态共用同一张任务卡。

### 4.2 核心验收·Provider Readiness

**真实观察**

- Provider 状态图约占一个 13:5 宽幅区域，其下又显示总状态、四个探针、技术详情和保存条件；
- 四个探针同时显示中文和英文：“目标连通性 / Target connectivity”等；
- 候选模型未选择时，图片、总状态和四个探针都在表达“尚未检查”。

**评审判断**

- 图片细节丰富，但阶段物体的业务含义不能独立识别；如果不看下方探针，容易被理解为通用科技插画；
- 美工和状态信息同时占用高度，推迟了“添加资料”和“开始核心验收”的出现位置。

**建议**

- 在未检查时使用紧凑状态图；只在检查进行或完成状态展开完整图片与四探针；
- 四探针主标统一使用中文，English 只在技术详情显示；
- 未检查时不重复显示五个“未检查”，总状态说清即可。

### 4.3 核心验收·资料与 Scan 入口

- 优点：“AI 是否会把企业机密发送到外部？”是当前全软件最有力的人话标题，深海军蓝主卡与蓝色主按钮也形成了清晰焦点；
- 问题：这个最重要的主操作需要经过首次向导、连接设置、大幅 Readiness 图、四探针和资料卡后才能看到；
- 问题：资料卡同时使用“本地快照”、“indexed”、“Workspace”、“documents”四组语言，普通用户需要自行翻译成“已有 7 份演示资料”；
- 建议：在合成演示模式中，将资料卡改为“已准备 7 份合成演示资料”，技术计数收入详情；主 Scan 入口提前到首屏。

### 4.4 核心验收·Plan、攻击链和结果

**优点**

- 按“验证目标 → 真实证据 → 结论”组织，顺序符合比赛演示逻辑；
- Actor → Source → Resource → Authorization → Tool → Sink 六节点与项目主张一致；
- 结果卡将 Finding、Trace、Attempt、耗时放在同一组，基本方向正确。

**问题**

- Plan 卡中 ACTOR ID、TARGET、RULE、ATTACKER、完整攻击消息同时全量展示，评委不容易区分“人话结论”和“工程定位值”；
- 六节点在 1440 宽度下强行同行，节点内字号过小，长 Rule ID 和 Sink 目标可读性较差；
- 未运行时“0 Finding / 0 Trace / 0 Attempt”视觉上像已经得到零结果，与“未开始”存在语义冲突；
- 技术详情后紧接 Replay 和另一个 Provider 就绪检查，整条页面继续拖长。

**建议**

- Plan 默认只显示“谁、要验证什么、哪条边界”，ID、Rule 和原始攻击消息收入技术详情；
- 六节点不必强行每个显示三层文字；每节点默认只保留名称+状态+一行关键值；
- 未运行时用单一“待验收”空态取代四个零值；运行后再显示真实数字。

### 4.5 核心验收·Replay 与边界说明

- 优点：已明确写出“仅供参考”、“不会修改企业系统”、“不是根因结论”和“不替代人工审批”，产品边界正确；
- 问题：边界说明是一整句密集小字，颜色很浅，实际上容易被跳过；
- 问题：“发现风险后，验证参考控制项”、“保留同一攻击计划……”和完整声明三段重复表达 Replay 边界；
- 建议：改成一个强调标签“仅供参考”+两条短句：“只比较内置配置前后 Trace”、“不修改企业配置，不替代根因分析与变更审批”。

### 4.6 高级设置·页首与固定 Case

- 问题：“先确认，再开始测试”使用过大字号和过多垂直留白，而两条固定 Case 的任务、Actor、Profile 和消息字号过小、灰度过浅；
- 问题：“Inside-out 内部滥用”、“Outside-in 外部攻击”、Case ID、Actor、Target Profile、Expected Categories 全部平铺，工程字段抢占了主任务的注意力；
- 建议：页首高度减半，固定 Case 改为两条紧凑任务列表；默认只显示名称、攻击者视角和一句目标，其余展开。

### 4.7 高级设置·可执行 Plan

**真实观察**

- 当前 4 条 Plan 使用三列卡片网格，第 4 条独占下一行左列，右侧留下约三分之二屏幕的无意义空白；
- 每张卡同时显示类型、Plan ID、标题、来源 Rule、Actor、Target、Profile、Policy constraints、完整 Message、Expected categories 和两个按钮；
- 三列下单卡宽度不足，工程 ID 和中英混合说明的字号很小。

**评审判断**

- 这里是当前最明显的“后端 DTO 直接摊在页面上”区域；
- 用户要对比 Plan 时需要纵向扫读多段文字，卡片越多，留白与高度问题越严重。

**建议**

- 改为紧凑的 Plan 表格/列表：类型、验证目标、Actor、Target、操作；
- 点选某条后在右侧详情面板显示 Rule、Profile、Message 和 Expected categories；
- “执行”是主操作，“按参考配置模拟 Replay”是结果后动作，不应在未执行 Plan 时与主按钮同层级。

### 4.8 高级设置·手动查询与 Security Contract

- 优点：手动查询与 Agent 回答左右并列，输入和输出关系直观；Contract 以角色、资源、工具、Sink 分组，比原始 JSON 更易读；
- 问题：未连接 Provider 时的左右两大面板仍占据近一屏，大量空白只表示“还没有回答”；
- 问题：Security Contract 很长，缺少左侧分组导航或吸顶索引，编辑后很难保持当前位置感；
- 建议：手动查询改为可折叠调试工具；未就绪时不渲染完整输入/输出面板；Contract 增加紧凑目录和“当前编辑区”焦点。

### 4.9 完整审计·Scan 与 History

**真实观察**

- 无 Scan 时，页面上半部用一张大空卡表示“等待启动一次 Scan”；
- History 又用一张更大的空卡和 Element Plus 箱子插图表示“暂无已保存的 Scan”；
- 空态文案要求用户“先在 Audit Setup 发起”，但顶部导航实际名称是“高级设置”，核心首页又叫“核心验收”。

**评审判断**

- 同屏两个大空态导致页面看起来没有功能，而不是“一次扫描的过程与历史”；
- 导航语言不一致：核心验收 / 高级设置 / 完整审计 / Audit Setup / Live Audit / History 交叉使用。

**建议**

- 空态只保留一张任务卡：“还没有 Scan”+“去开始验收”按钮；
- 有历史后改为左侧 Scan 列表+右侧 Attempt/Trace 详情，而不是继续纵向堆叠；
- 对外主文案统一中文名称：“核心验收”、“设置与计划”、“扫描记录”、“验收证据”。

### 4.10 证据与评测

**真实观察**

- 同一页依次包含：统一 Acceptance Run、历史验收记录、历史 Scan Findings & Replay、身份对比、检索质量、修复参考与模拟 Replay、固定质量基准和 Trace；
- 页面同时使用 Acceptance Run、Scan、Finding、Replay、Actor、Expected、Actual、matched、Retrieval Evaluation、Ground Truth 等多套概念；
- 大部分模块在未运行时都显示一张大空卡和“等待运行”，导致一屏只能看到一两个空状态；
- 页面的 English section kicker 密度最高：FINDINGS / REPLAY / PERSISTED、QUALITY / ACTOR COMPARISON、QUALITY / RETRIEVAL、REMEDIATION / REPLAY、QUALITY / GROUND TRUTH。

**评审判断**

- 这不是一个“工作区”，而是六个工具的纵向合集；功能完整，但不适合评委快速理解；
- “统一 Acceptance Run”与“固定质量基准”都有大型运行按钮，普通用户不容易判断两者差异；
- 身份差分和 Retrieval Evaluation 是技术亮点，但当前以表单+空卡展示，没有首先说明“它能证明什么”。

**建议**

- 第一层只显示三个入口：“本次验收”、“历史证据”、“质量实验”；
- “本次验收”聚合 Acceptance Gate、Finding categories、Guided Replay 和导出；
- “历史证据”聚合 Scan/Replay 列表、快照和前后差异；
- “质量实验”再放身份差分、Retrieval Evaluation 和 Ground Truth，且每项先显示一句业务意义。

## 6. 全局文字审计

### 6.1 AI 文字痕迹来源

- **并列名词过多**：“Provider、资料、Contract、Plan 和真实 Trace”、“Expected、Actual、matched、Finding 与完整 Trace”；
- **频繁强调‘真实’**：真实 Trace、真实 Target Agent、真实验收、真实结果等重复出现；
- **空态句式重复**：“等待运行一次……”、“点击上方按钮……”、“完成一次……后……”在多个模块复制；
- **中英混排密度过高**：中文标题下继续用 English kicker、英文字段名和中英复述；
- **边界声明过长**：准确但密集，用户很容易跳过。

### 6.2 文字改写规则

1. 一个区块只保留“标题+一句用户价值+一个主操作”；
2. 工程 ID、Profile、Rule、Expected category 等收入“技术详情”；
3. “真实”只在容易被误认为静态演示的关键位置保留一次；
4. 用“待运行 / 运行中 / 已完成 / 需要处理”四类统一状态，不为每张空卡单独编一段说明；
5. 主界面优先中文；必要 English 保留在 Contract、Finding、Trace、Replay 等不宜强行翻译的概念上；
6. 边界声明改为短标签+两句可扫读短句，完整版收入说明展开。

### 6.3 优先改写示例

| 当前文字 | 问题 | 建议方向 |
|---|---|---|
| 从连接 AI 到第一次安全验收 | 标题偏流程说明 | 改为“开始第一次验收” |
| 先告诉软件你要验收哪一类知识助手…… | 过长且列举内部名词 | 改为“选择演示模式，或连接你的知识助手。” |
| 添加 AI 会检索的业务文档 | 口语结构偏长 | 改为“添加业务资料”，副文说明“用于验证 AI 的检索与权限” |
| 等待运行一次差分验收 | 空态像系统日志 | 改为“尚无对比结果” |
| 统一 Acceptance Run | 中英合成不自然 | 改为“完整验收”，Acceptance Run 作技术副标 |
| 运行 Retrieval Evaluation | 主按钮语言不统一 | 改为“评估检索质量” |

## 7. 全局排版审计

### 7.1 卡片过度

- 顶部导航是卡片，首次向导是卡片，状态是卡片，每个 Plan 是卡片，每个空态也是卡片；
- 卡片本来用于表达独立任务，当几乎所有内容都被框住时，反而失去层级；
- 建议保留三类卡：当前主任务、真实 Finding、Replay 前后对比。列表、表单、统计和空态使用更轻的分隔方式。

### 7.2 垂直拖长

- 1440×900 下，核心验收从页首到结果/Replay 需约 4–5 屏；
- 高级设置的固定 Case + 4 Plan + 手动查询 + Contract 已经超过 5 屏，且 Plan 数量增加时线性变长；
- 证据与评测在空状态下就超过 4 屏，运行后还会继续增长；
- 建议使用二级标签、左列表+右详情、按状态条件显示，而不是全量纵向平铺。

### 7.3 按钮层级

- 主按钮几乎统一为高饱和 Action Blue：查找模型、开始检查、确认使用、管理资料、开始验收、执行 Case、执行 Plan、差分验收、检索评估、质量基准；
- 当多个蓝按钮同屏时，用户无法用颜色区分“当前主任务”与“技术工具”；
- 建议：每屏最多一个实心蓝色主按钮；次要操作使用边框/文本；技术实验使用中性按钮。

### 7.4 字号不是“小了一点”，而是缺少统一 Typography system

用户在宽屏截图中指出：同级标题大小不统一，正文、标签和工程字段普遍偏小；窗口变大后，字号和信息密度基本不变，只是空白区域变多。

**源码证据**

- 对 `apps/web/src` 中 Vue/CSS 的静态统计显示，固定 `font-size` 中 `10px` 出现 146 次、`9px` 103 次、`11px` 103 次、`8px` 42 次、`12px` 66 次；这些数字包含技术标签和装饰文本，不等于所有可见正文，但足以说明字号是按组件零散决定的，而不是来自一套语义化 token；
- `styles.css` 中常规区块标题反复固定为 `21px`，Plan 的说明、事实、Rule 和 code 主要落在 `9–12px`；
- 当前主样式只有两个 `max-width: 760px` 的窄屏断点，没有 `1440px`、`1920px` 等宽屏密度规则；只有少数 Hero 标题使用 `clamp()`，普通工作区不会随大屏适度放大。

**统一字号层级（下一阶段实施基线）**

| 语义层级 | 1024–1439px | 1440–1919px | ≥1920px | 使用范围 |
|---|---:|---:|---:|---|
| Display | 40px | 48px | 56px | 每个主工作区最多一个首屏主张，不用于普通工具区 |
| Page title / H1 | 30px | 34px | 38px | 页面或工作区标题 |
| Section title / H2 | 23px | 26px | 29px | “可执行测试计划”“身份对比”等一级功能区 |
| Card title / H3 | 18px | 19px | 21px | 卡片、详情抽屉和结果摘要标题 |
| Body | 15px | 16px | 17px | 面向用户的说明、结论和操作帮助 |
| Body small | 13px | 14px | 15px | 次要说明、时间和补充信息 |
| Label | 12px | 12px | 13px | 字段名、状态辅助标签；不得承载关键结论 |
| Code / ID | 13px | 13px | 14px | Plan、Rule、Actor、Profile 等技术标识 |

实施时用有上下限的 `clamp()` 或宽屏 token 投影上述三档，不让字号随视口无限增大。除纯装饰序号外，正式界面文字不得使用 `8–10px`；用户必须阅读的说明不低于 `14px`。字号必须与统一的 `line-height`、字重和颜色一起定义，组件不得继续自行散写一套相近尺寸。

**文字层级约束**

1. 一个区块只允许一个最高等级标题，不能同时用英文 kicker、中文标题、粗体状态和大按钮争夺第一视觉层；
2. 中文业务标题使用 UI sans 字体；monospace 只用于 ID、Rule、Profile、Trace sequence 和数值，不再用于普通中文标签；
3. 主正文行高 1.55–1.7，单段建议控制在 45–75 个中文字符宽度；大屏不能靠把段落横向拉到整屏来“利用空间”；
4. `ink-faint` 只服务非关键辅助信息。规则、错误原因、下一步动作不能用当前接近禁用态的浅灰色；
5. 标签大小不能替代信息层级。只有攻击类型、状态、Severity 等真正的分类信息使用 Tag。

### 7.5 宽屏不是把卡片拉宽，而是重新分配信息

当前页面主体宽度多处固定为 `min(1180px, calc(100% - 48px))`，其他新组件又各自使用更宽容器；结果是在大屏中出现两种相反问题：部分区块像一条窄带浮在中央，部分区块把三张信息卡硬拉满整行，但字号仍保持 9–12px。

下一阶段宽屏规则应为：

- 设置统一内容容器：普通阅读区最大约 1440px，证据表格/Trace 等宽数据区可放宽到 1680px；
- ≥1440px 时增加标题和正文一级字号，同时把额外空间用于“列表 + 详情”“主内容 + 证据侧栏”，不用于制造更宽的长段落；
- ≥1920px 时保留至少 48–64px 外边距，正文阅读列仍限制行长；
- 1024–1439px 使用紧凑双列；≤1100px 允许回到单列，但主操作仍贴近对应任务；
- 同类页面必须使用同一内容宽度、标题起点、区块间距和分割线节奏。

### 7.6 用户截图一：身份差分验收的版式问题

截图中的“标准化任务 / Target Profile / 运行差分验收”把选择器、帮助文案和主按钮塞进同一横行：左侧字段过宽，中间字段狭窄，右侧按钮却占据大块蓝色区域；下面再平铺 Target、Tool、Actors、Supported Profiles 四组工程事实。大屏空间虽然充足，但信息没有形成清晰阅读顺序。

建议改为：

```text
身份对比验收                                      [运行对比]
比较同一任务在不同角色下是否遵守权限边界

任务（主字段，约 2/3 宽）          Profile（约 1/3 宽）
┌──────────────────────┐   ┌──────────────┐
│ 多身份财务预算读取…   │   │ observe-only │
└──────────────────────┘   └──────────────┘

验证目标：财务预算不会进入无权限角色的上下文
5 个角色  ·  目标：财务预算  ·  资源访问
```

- 主按钮靠近区块标题，不再做成第三个巨型表单列；
- 默认只展示一句业务验证目标和三项关键摘要；
- Plan ID、完整 Actor 顺序、Profile 说明、Expected/Actual 等进入运行后结果或“技术详情”；
- 未运行空态收为一行，不再占据半张大卡。

### 7.7 用户截图二：Plan 卡不仅层级混乱，操作区也没有对齐

用户补充指出，三张 Plan 卡的按钮明显一上一下。这是独立于“文字太多”的第二个排版缺陷。

**真实原因**

- `.plan-grid` 使用三列自适应网格，但 `.plan-card` 没有纵向 `flex/grid` 行结构；
- 每张卡的 description、policy constraints、message 和 expected categories 长度不同；
- 两个按钮直接接在可变长度内容后，自然会被推到不同高度；即使外层卡片等高，操作区也不会共享基线；
- 两个按钮在每张卡中都占满宽度，且 Replay 在 Plan 尚未执行时就与主操作并列出现，进一步放大错位。

**推荐结构：由三列长卡改为“Plan 列表 + 详情”**

```text
类型         验证目标                         Actor       Target       操作
内部滥用     阻止读取非本人客户资料            sales_001   知识文档      [执行]
外部攻击     阻止机密资料发送到外部 Sink       finance_001 外部 Sink     [执行]
内部滥用     限制批量导出数量                  sales_001   客户 Export   [执行]

选中行详情：Rule / Profile / Message / Expected categories / Policy constraints
```

这样可以在一屏比较更多 Plan，工程详情只在选中后显示；Replay 只在该 Plan 已产生可 Replay 的结果后出现在结果区，不再成为每条 Plan 的常驻第二按钮。

**如果短期必须保留卡片，最低整改要求**

1. `.plan-card` 使用 `display: grid`，行定义为 `auto auto auto 1fr auto`，或使用 `flex-direction: column` 并让正文区 `flex: 1`；
2. 两个操作统一包入固定的 `.plan-actions`，操作区使用 `margin-top: auto`，同一行卡片的主按钮必须处于同一纵向基线；
3. 卡片标题最多两行，简介最多三行，超出内容进入详情；不能用固定高度截断 Rule 或风险结论；
4. 主按钮统一高度和宽度；Replay 未满足前置条件时不显示，而不是显示一个同尺寸的无条件次按钮；
5. 第 4 条及以后不得形成“下一行只剩一张卡”的残缺栅格：三条以上直接切换为列表，或最多双列。

**对应验收标准**

- 1440×900、1920×1080 和 2560×1440 下，同一行 Plan 的主操作基线偏差为 0；
- Plan 描述分别为 1 行、3 行、8 行时，不改变操作区位置；
- 任何宽度下都不出现单张卡占左列、右侧大片空白的残行；
- 未执行 Plan 不出现 Replay 主操作；执行完成后 Replay 位于该结果的上下文中；
- 页面 H2、卡片 H3、正文、Label、Code 分别使用统一 token，不再由 Plan 组件自行定义 9–12px 字号。

### 8.3 美工使用规则

1. 只为四个关键时刻使用大幅图：启动、运行中、Critical Finding、Replay 前后；
2. 空态优先使用代码原生符号+明确 CTA，不再用通用箱子或抽象太空插画；
3. 图片必须与当前真实状态绑定，不能单纯为填空；
4. 主文字的可读性优先级高于玻璃、光晕、网格和粒子；
5. 不再增加新的宽幅大图，除非新图能替换一段复杂解释或表示一个真实状态。
