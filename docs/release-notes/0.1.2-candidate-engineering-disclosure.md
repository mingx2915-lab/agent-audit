## Why these findings remain

- The Tauri stack resolves to Tauri `2.11.5`, `tauri-runtime-wry 2.11.4`, Wry `0.55.1`, GTK `0.18.2`, and GLib `0.18.5`. Wry's [GTK4/WebKit6 migration](https://github.com/tauri-apps/wry/pull/1767) remains open and changes APIs and Linux system packages. The separate [GTK 0.19 update](https://github.com/tauri-apps/wry/pull/1843) is still a draft, waits on upstream dependencies, and raises the MSRV to Rust 1.92; this project tests Rust 1.88. Neither is a released, compatible backend update for this candidate.
- The locked `tauri-utils 2.9.3` requires the `urlpattern 0.3` line, while `urlpattern 0.6` is a pre-1.0 breaking-version jump. There is no released compatible Tauri dependency graph to update to, so forcing it would be an unverified API override.
- `glib`'s unsoundness advisory lists `>=0.20.0` as patched, but the current GTK3/Wry stack pins GLib 0.18.5; the application's direct reachability assessment is recorded above ([RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429)).
- `pdf-extract` was updated to compatible patch release `0.12.1`, but its declared `lopdf ^0.42` constraint keeps the PDF import path on `lopdf 0.42.0` → `ttf-parser 0.25.1`. RustSec lists no patched `ttf-parser` version and identifies `skrifa` as an alternative; switching the parser needs a separately tested PDF extraction change ([RUSTSEC-2026-0192](https://rustsec.org/advisories/RUSTSEC-2026-0192)).
- The latest online scan ran `cargo-audit 0.22.2` against the RustSec database updated 2026-09-26; its artifact is attached to [run 36322348763](https://github.com/mingx2915-lab/agent-audit/actions/runs/36322348763). The workflow is intentionally not disabled or allowlisted. A fresh scan is required before a later release because advisories and dependency graphs can change.
