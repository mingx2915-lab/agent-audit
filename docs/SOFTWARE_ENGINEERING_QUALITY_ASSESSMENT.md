# 知盾 AgentAudit 软件工程质量评估与下一阶段建议

- 文档性质：只读工程审计与方向约束，不代表新功能已启动
- 评估日期：2026-08-28
- 当前里程碑：M6 本地双平台产品化
- 当前活动功能：F-035 企业 AI 接入与首次验收向导
- 适用范围：当前仓库、Windows Desktop 实现、已有自动化与人工验收记录

> 时间线说明：本文是 2026-08-28 的历史工程评估，其中“无 CI”、“无 migration”、“无诊断包”、“Linux 未验收”和当时的测试数量不是当前状态。后续 F-051–F-056 已分别补齐发布证据、Windows 生命周期、诊断、migration、Linux 真实工件与供应链证据；当前事实以 `docs/STATUS.md`、`docs/ACCEPTANCE.md` 和 F-057 功能文档为准。

## 1. 结论先行

知盾 AgentAudit 当前已经形成一个具有真实业务链路、明确安全不变量、桌面交付能力和较强自动化证据的竞赛级企业 AI 安全验收原型。它不再是“Prompt 输入—模型回答—再让模型打分”的页面演示，而是能够真实执行：

```text
企业资料 / 合成资产
→ Retrieval
→ Authorization
→ Tool Call / Sink
→ Trace
→ Contract Checker
→ Finding
→ 修复配置
→ 同 Plan Replay
```

当前软件已基本达到以下层级：

- 竞赛技术原型：达到；
- Windows 可演示桌面软件：基本达到；
- 小企业受控试用版：接近，但仍需稳定性、诊断和新手验收补强；
- 可长期无人维护的成熟企业产品：尚未达到。

差距主要不在“功能数量”，而在以下证据尚不完整：

1. 长时间运行、重复执行和资源泄漏；
2. 进程崩溃、磁盘异常和写入中断后的恢复；
3. 历史数据、Workspace 和导入规模增长后的性能；
4. 安装升级、数据库迁移和旧数据兼容；
5. 陌生用户是否能独立完成首次验收；
6. Linux 安装包、Secret Service 和跨平台迁移的真实环境证据；
7. 现场故障时可供管理员理解的日志与诊断材料。

因此，下一阶段应优先把现有能力证明得更可靠、更容易使用，而不是继续扩张成通用企业资产扫描平台。

## 2. 本文不做什么

本文不自动启动新功能，不修改 F-035 的完成状态，也不把建议写成已经实现的事实。

本文不会建议当前项目引入以下不必要复杂度：

- 微服务、消息队列、Kubernetes 或分布式锁；
- 云端 Sentry、强制 Telemetry 或外部日志平台；
- 为单机 SQLite 提前建设高并发数据库架构；
- 任意局域网扫描、自动接管企业系统或广泛 Connector；
- 无限重试、静默 fallback 或用后处理掩盖真实失败；
- 为了测试而破坏用户真实 Workspace、磁盘或系统配置。

## 3. 独立的软件工程评价模型

在不考虑本项目的情况下，一个成熟桌面企业软件应至少从以下十个方面评价。软件质量不能只等同于“功能跑通”或“测试数量多”。

### 3.1 需求与范围治理

需要回答：

- 软件为谁解决什么问题；
- 明确支持和不支持哪些场景；
- 每项需求是否对应可观察的验收结果；
- 新需求是否仍服务产品主线；
- 文档、代码、测试和发布状态是否一致。

成熟表现是：需求可以追溯到实现与验收，未完成的工作不会被包装为完成，扩展想法有明确的 Parking Lot。

### 3.2 架构与边界

需要检查：

- UI、业务规则、模型 Provider、文件系统和数据库是否职责分离；
- 外部输入是否只在信任边界校验；
- 确定性业务规则是否独立于 LLM；
- 状态是否有唯一事实来源；
- 某个模块失败是否会污染其他模块；
- 桌面壳是否只负责系统集成，而不复制业务判断。

架构的目标不是“层数越多越好”，而是让变化和故障停留在合理边界内。

### 3.3 功能正确性

不仅要验证正常输入，还要验证：

- 错误输入是否被正确拒绝；
- 权限允许和拒绝是否都能观测；
- expected、展示名称和模型回答是否无法篡改真实 Finding；
- 同一规则在 API、桌面、报告和 Replay 中是否保持一致；
- 用户取消、重复点击和刷新是否不会产生隐藏副作用。

### 3.4 可靠性与恢复能力

可靠性不是“没见过崩溃”，而是以下能力的组合：

```text
可靠性 = 正确执行 + 明确失败 + 数据一致 + 可恢复 + 无资源泄漏
```

需要验证：

- 重复启动与关闭；
- 长时间运行；
- 模型超时、断连、无效响应；
- 进程在写入前、中、后被终止；
- 文件锁定、只读目录、磁盘空间不足；
- SQLite 或 Workspace 损坏时的诊断；
- 失败后再次执行是否恢复，而不是必须重装。

### 3.5 性能与资源效率

至少要建立可复跑基线：

- Desktop 冷启动和热启动时间；
- 首次 Embedding 索引时间；
- 50 项导入的耗时；
- Guided Audit、Replay 和 24 Case Acceptance Run 耗时；
- 空闲和运行时内存；
- 连续执行后的内存、句柄和 Sidecar 进程数量；
- 历史记录增长后列表与详情读取耗时。

这些指标必须标明机器、模型、数据规模和测量方式，不能把单次最快结果当成稳定性能。

### 3.6 可用性与可访问性

可用性不能只由开发者判断，需要观察真实用户：

- 能否理解第一步；
- 是否知道应该导入什么；
- 是否能区分 AI Runtime、业务文档和 Workspace；
- 出错后是否知道下一步；
- 是否能找到 Finding 与 Replay；
- 任务完成率、耗时和求助次数；
- 125%/150%/200% DPI、1366×768 和窄窗口是否可操作；
- 键盘、焦点、长文本、双击和快速取消是否稳定。

### 3.7 安全与隐私

桌面企业软件至少要保证：

- Secret 不进入普通 JSON、Workspace、History、Trace 或报告；
- 只读取用户明确选择的文件和明确填写的服务地址；
- 不把绝对来源路径写入可移动工件；
- 默认不扫描网络，不上传企业内容；
- 本地 API 只监听 loopback；
- 文件解析不执行宏、脚本和外部链接；
- 错误信息可诊断，但不泄露 Secret 或不必要的企业内容。

### 3.8 可维护性与可测试性

需要关注：

- 模块是否过度集中；
- API DTO 是否由共享契约约束；
- 核心规则是否能脱离 UI 测试；
- 测试是否依赖真实时间、固定机器路径和全局状态；
- 新功能是否必须修改巨大入口文件；
- 失败测试是否能快速定位责任模块。

文件大并不自动等于设计错误，但持续增长的大入口会增加冲突、回归和理解成本。

### 3.9 可运维性与可诊断性

企业管理员需要回答：

- Sidecar 为什么没有启动；
- 当前使用哪个 Workspace、Contract、Provider 和 Retriever；
- 最近一次操作失败在哪一步；
- 是否留下孤儿进程；
- 数据库是否可读；
- 如何导出不含 Secret 的诊断包；
- 如何备份和恢复。

健康端点只能证明进程就绪，不能代替日志、操作事件和故障上下文。

### 3.10 构建、发布与升级

需要验证：

- 构建依赖是否可复现；
- Windows/Linux 安装包是否在真实目标系统运行；
- 安装、卸载、升级和回滚是否保留 Workspace；
- 数据库与 manifest 是否具有版本和迁移策略；
- 旧版本数据是否能在新版本打开；
- 安装包、第三方依赖和许可证是否可审阅；
- 发布失败时能否回到上一版本。

## 4. 成熟度标尺

本文采用五级证据标尺，避免用主观的“不错”“差不多”代替事实：

| 等级 | 含义 |
|---|---|
| L0 | 没有明确设计或证据 |
| L1 | 已有设计、文档或局部实现 |
| L2 | 已实现并有单元/集成测试 |
| L3 | 已通过自动化主链、真实进程或真实构建工件验证 |
| L4 | 已在目标环境和真实用户场景中反复验证，形成稳定运行记录 |

L4 不等于“永远没有故障”，而是已知运行条件、失败模式和恢复手段均有实际证据。

## 6. 分项评估

### 6.1 产品主线与范围治理：L3，接近 L4

#### 已有优势

- `AGENTS.md`、`PROJECT.md`、功能编号和单一 In Progress 约束形成了稳定主线；
- Security Contract、Outside-in / Inside-out、全过程 Trace、Finding → Replay 四条主张清晰；
- 每个功能具有范围、非目标、API、验收标准和证据；
- 文档能够诚实保留 Linux、干净 Windows 和陌生用户验收债务；
- 没有把任意企业扫描、真实邮件外发或读取真实敏感数据混入比赛 MVP。

#### 主要缺口

- 长期功能较多，部分早期文档记录的历史测试数字与当前基线不同，需要继续把“历史证据”和“当前事实”区分清楚；
- 比赛版、受控试用版和未来企业版仍应在软件内进一步区分，避免用户把合成靶场能力理解成任意企业系统扫描能力。

#### 判断

这是当前项目最成熟的部分之一。防任务漂移机制明显强于普通竞赛项目。

### 6.2 核心业务正确性：L3

#### 已有优势

- Retrieval、Authorization、Tool Call、Sink、Trace、Finding 和 Replay 是真实执行链；
- Contract Checker 为确定性裁决，LLM 不直接决定最终 Finding；
- expected、Plan 展示字段和模型回答不能改写实际结论；
- secure/vulnerable、允许/拒绝身份、before/after 均有单元和集成证据；
- 24 Case Acceptance、Differential、Retrieval Evaluation 与 Guided Scan 使用统一运行时能力，而不是静态页面数据。

#### 主要缺口

- 当前受控攻击类别仍集中在项目定义的四条业务不变量，不应外推为覆盖全部 AI Security 风险；
- 真实企业业务 Tool、真实身份系统和企业知识源尚未接入，因此不能宣称已经验证任意企业部署。

#### 判断

作为比赛的核心技术闭环已经足够，并且是项目最具差异化的部分。此处不应继续无边界增加攻击类别。

### 6.3 架构边界：L3

#### 已有优势

- 采用单仓库、模块化单体，适合当前团队和比赛规模；
- Web、API、Desktop、Contracts、Workspace 与 Model Provider 边界清楚；
- Application、AI Runtime、Audit Workspace 三者已经分离；
- Tauri 只负责桌面生命周期、Credential Store 和文件对话框，不复制 Security Contract 判定；
- Provider Adapter、Retriever Protocol、Repository 与共享 DTO 为后续演进保留了替换边界。

#### 风险

- `App.vue`、`main.py` 与 `lib.rs` 已成为集成热点；
- 大型 Vue 组件和集中 CSS 会提高 UI 修改冲突与视觉回归风险；
- `create_app` 承担较多运行时装配和路由职责，未来继续增加功能会降低可理解性；
- 当前不需要全面重写，但后续应在真实变更压力出现时按业务工作区拆分，而不是再向入口文件堆积。

#### 判断

架构方向正确，复杂度仍可控制，但已经到需要限制入口继续增长的阶段。

### 6.4 自动化测试：功能覆盖 L3，耐久性覆盖 L1-L2

#### 已有优势

- 单元测试覆盖 Contract、Checker、Planner、Retriever、Provider、History、Import 与 Archive；
- 进程内集成测试覆盖 API → 服务 → Repository/Tool/Trace；
- Playwright 覆盖首次接入、模型连接、导入、Scan、Finding、Replay、History 和窄屏；
- Rust 测试覆盖 PDF/DOCX、加密、损坏、无文本和大小边界；
- 条件不满足的 Linux/Artifact 测试明确 skip，没有伪装为通过。

#### 关键区别

当前大量测试证明的是：

> 给定输入后，软件能得到正确结果。

尚未系统证明的是：

> 软件连续运行、反复失败、资源紧张或进程中断后，仍能保持性能和数据一致。

#### 缺失测试类型

- Soak Test；
- Stress / Capacity Test；
- Crash Recovery；
- Process Lifecycle Repetition；
- Memory / Handle Leak；
- Upgrade / Migration；
- Disk / Lock / Read-only 故障；
- 大历史数据性能；
- DPI、键盘和误操作可用性；
- 陌生用户任务测试。

### 6.5 可靠性与恢复：L2

#### 已有优势

- Provider 失败具有明确 502/503 语义，不重试、不 fallback；
- Red-Team Scan 有最多三轮、Finding 后停止和重复变体停止；
- Preview 无副作用；Import 使用候选索引和原子 catalog 写入；
- History/Acceptance Run 采用 append-only；
- Workspace 具备备份、纯 Preview、copy-as-new Restore 和显式 Activate；
- Sidecar 只监听 loopback，Desktop 关闭时清理自身进程树；
- 已对部分写入失败、Provider 错误和进程生命周期进行自动化验证。

#### 主要缺口

- 未形成 30 次或更多 Desktop 启停记录；
- 未验证连续 100 次核心工作流后的内存、句柄与响应时间；
- 未安全验证写入过程中终止 Sidecar/Desktop 后的磁盘状态；
- 未验证 SQLite 文件被锁定、只读或损坏后的用户恢复路径；
- 未验证操作系统睡眠/恢复、网络切换和模型运行时重启；
- 未建立“失败后无需重装即可继续”的系统级验收矩阵。

### 6.6 数据持久化、备份和升级：当前数据安全 L2-L3，升级能力 L1

#### 已有优势

- Workspace manifest 使用相对目录，可移动；
- Seed 仅在首次创建时复制，之后不覆盖 Contract/History；
- Import 不保存来源绝对路径；
- History 与 Acceptance Run 追加保存；
- ZIP 备份恢复已经覆盖文档、Contract、Profile、Ground Truth、History 与 exports；
- Restore 采用新 Workspace，不直接覆盖当前活动 Workspace。

#### 主要缺口

- SQLite 表目前以 `CREATE TABLE IF NOT EXISTS` 创建，尚未看到 schema version 和迁移序列；
- 未验证旧版安装升级到新版后继续读取 History、Acceptance Run 和 Workspace；
- 未形成损坏数据库隔离、诊断与从备份恢复的操作流程；
- SQLite 并发、锁等待和大记录量不是当前单机 MVP 的主矛盾，但需要容量实测后再决定是否调整。

### 6.7 性能与资源：L1

#### 已有事实

- 记录了部分 Scan、Benchmark 和 Acceptance Run 的 duration；
- 文件导入有限制：单批最多 50 项、原文件最大 20 MiB、标准化文本最大 2 MiB；
- Red-Team 最多三轮，避免无界模型循环。

#### 主要缺口

- 没有正式的启动时间指标；
- 没有内存和句柄基线；
- 没有 50 项接近边界的真实批量性能；
- 没有大 History / Acceptance 数据量测试；
- 没有同一机器、同一模型下的 p50/p95 记录；
- 没有明确的可接受性能预算。

#### 判断

当前不能说性能差，但也不能说已经证明性能稳定。缺的是测量，不是立刻优化。

### 6.8 用户体验：L2

#### 已有优势

- F-032 至 F-035 已重构视觉层级、连接模型流程和企业资料导入；
- 首次使用提供“合成演示”和“验收我的知识助手”双入口；
- 页面已说明应该导入 AI 会检索的业务文档，而不是模型目录或 Workspace；
- 真实 Windows 对话框和四格式导入已经由开发方人工完成；
- 390×844 E2E 验证了关键路径无横向溢出。

#### 未完成事实

- F-035 仍缺由未阅读源码的人完成五分钟首次任务；
- 真实原生文件错误路径仍缺人工证据；
- 尚无 125%/150%/200% DPI、1366×768、键盘导航和焦点顺序证据；
- 尚无误双击、快速取消、刷新、窗口最小化恢复等交互耐久测试；
- 当前 UI 仍包含较多高级能力，首次用户是否能忽略它们需要真实观察。

#### 判断

开发者已经能用，不等于普通企业管理员会用。F-035 剩余验收非常重要，不应被更多自动化测试替代。

### 6.9 安全与隐私：L3（受控范围内）

#### 已有优势

- 本地 Sidecar 只绑定 `127.0.0.1`；
- 企业 Provider 只连接用户明确填写的 origin，不扫描网络；
- Bearer Credential 使用系统 Credential Store，不写入 Workspace/History/Trace；
- 文档只读取用户显式选择的文件；
- PDF/DOCX 只抽取文本，不执行宏或访问外链；
- 绝对来源路径不进入 API、Workspace 和报告；
- Mock Mail/Sink 不真实外发；
- Finding 由确定性业务证据产生。

#### 边界

- 这证明的是项目定义范围内的数据与执行边界，不等于完成通用客户端安全审计；
- 尚未形成正式安装包签名、SBOM、依赖漏洞审计和恶意文件模糊测试证据；
- Linux Credential Store 仍缺真实 Secret Service 环境验证。

### 6.10 可观察性与支持：L1-L2

#### 已有优势

- `/api/health`、Desktop runtime status、Provider Readiness 和完整 Trace 可用于判断业务执行；
- History、Acceptance Run、JSON/Markdown 和 Workspace Archive 能保存业务证据；
- 用户可看到 Provider、Retriever、Contract 和 Finding 的主要事实。

#### 主要缺口

- 未看到完整的本地运行日志和轮转策略；
- 未看到统一操作 ID 将 Desktop 启动、API 请求、Provider 调用与错误串联；
- 未看到一键导出且自动脱敏的支持诊断包；
- Sidecar 启动失败、SQLite 异常和原生文件错误仍主要依赖即时错误文本；
- 当前 Trace 是安全业务证据，不应被误当成应用运行日志。

#### 建议原则

如后续确有现场支持需求，只实现本地、脱敏、可关闭的最小诊断能力，不引入云 Telemetry。

### 6.11 构建发布与跨平台：Windows L3，Linux L1

#### 已有优势

- Tauri Windows Desktop、PyInstaller Sidecar、release EXE 和 NSIS 已有构建与 smoke 证据；
- Desktop 关闭时清理自身 PyInstaller 进程树；
- Workspace 与安装目录分离；
- Windows/Linux 路径语义和 Linux build 脚本已有代码与条件测试。

#### 主要缺口

- 干净 Windows 机器安装、升级、卸载与数据保留仍需独立复核；
- Linux x86_64 `.deb`/AppImage、Secret Service 和跨平台 Restore 尚无真实环境证据；
- 仓库没有持续集成工作流，验收依赖本机人工串联；
- 当前未看到正式升级/回滚与数据迁移策略。

### 6.12 可维护性：L2

#### 已有优势

- API 业务模块数量合理，Contract、Provider、Retriever、Planner、Replay、History 分层明确；
- 测试规模已经接近生产源码规模，核心业务具备回归保护；
- 共享 TypeScript Contracts 降低前后端字段漂移；
- 功能文档可以在上下文压缩后恢复开发状态。

#### 维护热点

- `App.vue`、`styles.css`、`main.py` 和 `lib.rs` 是明显集中点；
- 多个 Web 组件超过 1,000 行，UI 状态和布局修改成本会上升；
- 不建议现在发动全面重构；
- 后续只有在一个新功能必须同时修改多个集中模块、或重复出现回归时，才按真实业务边界拆分。

## 7. 当前最重要的质量缺口

按比赛收益、小企业试用价值和实施成本综合排序：

### P0：完成 F-035 真实新手验收

必须完成：

- 一名未阅读源码和开发文档的人；
- 从空白状态开始；
- 只看软件页面；
- 完成连接 AI、添加资料、确认权限、执行 Guided Audit、找到 Finding/Replay；
- 记录总耗时、求助次数、卡点和误解；
- 不因测试失败临时口头解释页面之外的概念。

该项直接证明用户体验，比再增加几十个单元测试更有价值。

### P1：建立桌面极端稳定性与恢复验收

建议在 F-035 诚实收尾后，单独创建候选功能：

> F-036 桌面软件极端稳定性与可用性验收

它应是测试与修复功能，不是扩张产品业务范围。

### P2：最小本地诊断能力

只有在 F-036 证明“出了问题难以定位”后再实施：

- 本地滚动日志；
- 操作/进程关联 ID；
- 一键导出脱敏诊断包；
- 明确包含/不包含的数据；
- 不联网、不上传、不含 Secret 和完整企业正文。

### P3：升级与数据迁移

在准备对外发第二个版本前补齐：

- Workspace manifest version；
- SQLite schema version；
- 顺序 migration；
- 旧版本 fixture；
- 升级失败不破坏原数据；
- 备份后升级和显式回滚说明。

### P4：按证据拆分维护热点

只在继续开发确实受阻时进行：

- 按工作区拆分 `App.vue` 状态与 API 调用；
- 按路由域拆分 `main.py`；
- 按 desktop lifecycle / credential / picker / archive 拆分 `lib.rs`；
- 样式按组件或语义层组织。

不以文件行数作为立即重写理由。

### P5：真实跨平台发布证据

- 干净 Windows 安装/升级/卸载；
- Linux x86_64 真实 Secret Service；
- `.deb`/AppImage 启动、Sidecar 关闭和 Workspace Restore；
- Windows 备份在 Linux 打开，反向再验证；
- 没有真实环境时保持未完成，不用静态配置测试替代。

## 8. F-036 候选测试设计

以下是建议目标，不是当前已达到的结果。正式开始前仍需创建功能文档并保持只有一个 In Progress。

### 8.1 启动与进程生命周期

在隔离 `AGENT_AUDIT_HOME` 下执行：

- Desktop 启动/退出 30 次；
- 每次等待真实 Sidecar ready；
- 每次退出后检查 Desktop 与 Sidecar 进程树；
- 检查动态端口是否释放；
- 检查 Workspace manifest 和 SQLite 是否仍可打开；
- 记录启动耗时分布，不只记录平均值。

目标示例：30/30 成功启动，退出后孤儿进程为 0，Workspace 无损坏。该数字必须在实测后才能写入验收结果。

### 8.2 重复核心工作流

分成两条证据：

1. Deterministic Test Provider：连续执行 100 次 Guided Scan → Finding → Replay，验证状态、History、内存与句柄；
2. 本地真实模型：执行较小次数，例如 5-10 次，用于验证 Provider 真实波动，不追求虚假的 100% 确定性。

两种结果必须分开报告，不能用 Test Double 的稳定性冒充真实模型稳定性。

### 8.3 文件与容量边界

使用临时合成目录：

- 50 个混合支持/不支持文件；
- 接近 20 MiB 原文件边界；
- 接近 2 MiB 标准化文本边界；
- 重名文件、深层相对路径、长文件名、中文与特殊字符；
- 部分只读/锁定/损坏；
- 连续两次导入和取消；
- 导入后立即 Retrieval 与 Authorization。

不能使用用户真实企业文件，也不能故意填满系统盘。

### 8.4 崩溃与恢复

只在隔离 Workspace 中进行：

- Preview 阶段终止：不得产生写入；
- candidate index 构建阶段终止：旧 catalog/Retriever 可用；
- Workspace 写入阶段终止：重启后只能看到旧版或完整新版，不能出现半个 JSON；
- Acceptance Run 保存前后终止：不得产生伪 completed 记录；
- Desktop 在 Sidecar starting/ready 时关闭：无孤儿进程；
- 模型运行时退出、重启后，软件应显示失败并允许用户重新显式执行。

真实强杀只针对本次测试创建的精确进程与临时目录。

### 8.5 外部 Provider 故障

覆盖：

- connection refused；
- connect/read timeout；
- HTTP 401/403/429/500/502/503；
- 返回 HTML、空 body、截断 JSON；
- Tool Call 参数非法；
- 模型只返回文本、不执行 Tool；
- 模型处理中途被关闭；
- Readiness 成功后 Runtime 失联。

要求：不自动切换模型、不静默 fallback、不泄露 Credential、不把 Provider 故障伪造成安全 Finding。

### 8.6 SQLite、Workspace 与磁盘故障

采用临时目录或依赖注入模拟：

- 数据库锁定；
- 目录只读；
- 写入返回磁盘空间不足；
- JSON 截断；
- manifest 不合法；
- History 数据结构不兼容；
- 备份中途失败；
- Restore 后校验失败。

不在用户真实 Workspace 上执行破坏性实验。

### 8.7 性能和资源基线

固定记录：

- OS、CPU、RAM、磁盘、模型和版本；
- 冷启动/热启动；
- 首次索引/重复打开；
- 单次 Guided Audit/Replay；
- 24 Case Acceptance；
- 50 项导入；
- 100 次 deterministic 流程前后的内存、句柄和数据库大小；
- History 100/1,000 条时列表与详情耗时。

先测量再定门槛，不能先写一个漂亮数字再调整实现迎合数字。

### 8.8 可用性极端与误操作

覆盖：

- 1366×768；
- Windows 125%、150%、200% DPI；
- 390×844 继续作为布局回归，而不是桌面真实使用证明；
- 键盘 Tab 顺序、Enter、Esc；
- 快速双击主按钮；
- 请求中取消、切换页面和刷新；
- 20-100 字符的企业地址、模型名和文件名；
- 很长错误信息；
- 空态、部分成功和完全失败；
- 用户不知道 Security Contract、Workspace、Retriever 等术语。

### 8.9 陌生用户任务

建议至少记录 5 名非开发参与者，但比赛前若人员有限，先完成 1 名真实用户也比开发者自测更有价值。

记录字段：

- 是否完成；
- 用时；
- 求助次数；
- 第一个错误点击；
- 无法理解的术语；
- 是否能复述 Finding 表示什么；
- 是否能找到 Replay；
- 是否误以为软件扫描了整个企业系统。

访谈记录只写观察事实，不把参与者意见包装成市场普遍结论。

## 9. 建议的质量门槛表达方式

后续不要只写“测试通过”，建议按以下结构记录：

```text
测试对象：Windows Desktop release artifact
环境：Windows 11 / CPU / RAM / 本地模型
数据：隔离 Workspace / 合成文档数量
执行：启动退出 30 次
结果：成功次数、失败次数、p50/p95、孤儿进程、数据校验
边界：未覆盖 Linux、睡眠恢复或系统断电
工件：命令、日志、JSON/Markdown、截图索引
```

对于性能、稳定性和用户体验，必须同时写环境与边界。

## 11. 最终判断

### 已经可以确信的内容

- 项目主线明确，任务漂移控制良好；
- 核心安全判定具有真实 Trace 和确定性证据；
- 当前 Windows 桌面主链已经能运行；
- 自动化功能回归显著强于普通竞赛项目；
- 作为比赛核心技术 Demo 已经足够。

### 目前不能宣称的内容

- 长时间运行无内存或句柄泄漏；
- 崩溃和磁盘异常后一定自动恢复；
- 大规模 History/Workspace 下性能稳定；
- 任意小企业员工无需培训即可使用；
- Linux 版本已经真实可用；
- 安装升级不会影响任何旧版本数据；
- 已达到成熟商用企业软件等级。

### 下一步原则

1. 先完成 F-035 的陌生用户五分钟任务和真实原生错误证据；
2. 再创建一个范围克制的 F-036，专门做稳定性、恢复性、性能和可用性验收；
3. 只修测试暴露的真实问题，不顺手重写架构；
4. 不增加新的企业扫描类别；
5. 所有极端测试使用隔离 Workspace、合成数据和精确进程边界；
6. 未测过的指标绝不写成已达到。

这条路线最符合当前项目阶段：从“功能完整的竞赛原型”继续走向“可交给小企业试用的可靠桌面软件”。
